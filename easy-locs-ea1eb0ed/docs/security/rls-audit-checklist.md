# RLS Audit Checklist

Procedure to audit Row-Level Security for every sensitive table and produce
an automated regression suite.

## 1. Enumerate sensitive tables

Run the following in the Supabase SQL editor (or via the service-role
client) to list tables in sensitive schemas and whether RLS is enabled:

```sql
select n.nspname as schema,
       c.relname as table,
       c.relrowsecurity as rls_enabled,
       (select count(*) from pg_policy p where p.polrelid = c.oid) as policy_count
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where c.relkind = 'r'
  and n.nspname in (
    'public', 'identity', 'wallet', 'orbit',
    'marketplace', 'commerce', 'property',
    'onboarding', 'support', 'notification',
    'system', 'analytics'
  )
order by rls_enabled, policy_count, schema, table;
```

Expected invariants:

- Every table in the listed schemas has `rls_enabled = true`.
- Every table has ≥ 1 policy; for user-owned data, ≥ 1 policy per `(SELECT,
  INSERT, UPDATE, DELETE)` command we expect to allow.
- Tables we intentionally leave permissive (e.g. public taxonomy / SEO
  catalogs) must appear in a documented whitelist.

## 2. Three-persona test matrix

For each sensitive table, write tests that cover:

| Persona | Expected |
| --- | --- |
| `anon` (no JWT) | Reads limited to public rows (or denied). Writes denied. |
| `authenticated` owner | Reads / writes rows they own. |
| `authenticated` non-owner | Denied for owner-scoped data. |

Implementation options:

- **pgTAP** (`supabase/tests/*.test.sql` using `plan` / `ok` / `lives_ok`).
- **Deno test harness** that talks to a local Supabase stack with three
  different JWTs (service role + two user JWTs).
- Programmatic fuzz: for every sensitive table, emit an autogenerated test
  that asserts anon `select` returns 0 rows and anon `insert` returns 42501.

## 3. CI integration

Add a CI job that boots `supabase start` and runs
`supabase db test` (for pgTAP files) plus the Deno/Vitest suite. Gate PRs
on a green run. Target is 100 % of tables in the sensitive schemas list.

## 4. Ongoing hygiene

- Every new migration that adds a table in a sensitive schema must include
  `alter table … enable row level security;` and at least one policy, or an
  entry added to the whitelist with rationale.
- Add a migration-time assert (pre-commit or CI lint) that rejects
  `create table` in a sensitive schema without the matching RLS enable.
