## 1. Edge Functions — JWT + Rate limiting

### Current state

- 223 edge functions under `supabase/functions/`.
- Supabase default is `verify_jwt = true`. 35 functions explicitly override it
  to `false` in `supabase/config.toml`; those are routers (which verify JWT
  internally via `_shared/edge-auth.ts`), third-party webhooks
  (Stripe/SES/Plaid/Inngest/GitHub — signature verified in code), and
  `pg_cron` dispatchers (service-role header).
- Shared middleware:
  - `_shared/edge-auth.ts` → `requireAuthenticatedUser`, `requireServiceRole`
  - `_shared/with-rate-limit.ts` / `_shared/server-rate-limiter.ts` → IP-based
    + user-based + tier-aware rate limiting, standard `X-RateLimit-*` headers,
    and `Retry-After` on 429.
- Inventory summary (from `edge-functions-auth-inventory.md`):
  - JWT-protected: **192 / 223** (86 %)
  - Signature-verified webhooks: **7**
  - Public (no auth wrapper and `verify_jwt=false`): **24**
  - Rate-limit coverage: **80 / 223** (36 %)

### Gaps

1. Rate-limit coverage is only ~36 %. All public-facing routers and heavy AI
   endpoints should use `withRateLimit`.
2. The 24 public-mode functions flagged by the inventory need a classification
   pass: either move behind a router, wrap with `withRateLimit` + an auth
   check, or add to the explicit whitelist with a documented reason.
3. Consolidation of 175 → <60 edge functions is tracked as a separate task.
   Rate-limit + auth audit must be re-run after consolidation.

### Actions taken in this task

- Added `supabase/functions/_manifest.ts` — an **explicit** ground-truth
  classification of every security-relevant edge function (auth mode +
  rate-limit wrapper presence + reason). No regex inference.
- Added `scripts/security-inventory-edge-functions.ts` which cross-checks
  the manifest against `config.toml` and the actual handler source, and
  fails (exit 2) on any drift (rate-limit claimed but wrapper missing,
  config.toml verify_jwt inconsistent with the declared auth mode, etc.).
- Added `supabase/functions/_shared/webhook-signature.ts` with
  `verifyHmacSha256` and a `constantTimeEqual` helper backed by
  `node:crypto`'s `timingSafeEqual`.
- Hardened four public-facing functions:
  - `command-email-intake`: now supports HMAC-SHA-256 over the raw body
    (preferred) and falls back to a constant-time shared-secret compare,
    wrapped with `withRateLimit` (60 req/min).
  - `command-approval-webhook`: constant-time compare on the
    `x-internal-secret` JSON path, wrapped with `withRateLimit` (120/min)
    to throttle brute-force attempts against the per-request tokens.
  - `receive-email`: shared secret now compared in constant time and the
    whole handler is rate-limited; the missing `verify_jwt=false` entry
    was added to `config.toml`.
  - `command-monitoring-cron`: constant-time compare on the internal
    secret header + `verify_jwt=false` declared in config.
  - `public-api`: wrapped with `withRateLimit` (120/min).
- Produced `edge-functions-auth-inventory.md` with current posture:
  37 manifested functions (0 config mismatches, 0 rate-limit mismatches,
  0 auth mode mismatches) and 186 functions flagged as **unclassified**
  — the honest, surfaced gap that follow-up #772 has to close.

## 2. RLS — Supabase Row-Level Security

### Current state

- Domain schemas enabled in PostgREST: `identity`, `wallet`, `orbit`,
  `marketplace`, `commerce`, `property`, `onboarding`, `support`,
  `notification`, `system`, `analytics`, plus `public` compat views.
- Only one SQL-level test file today (`supabase/tests/execution_tasks_v2.test.sql`).
  There is no systematic RLS-per-table regression suite.

### Gaps

- No programmatic enumeration of "tables missing RLS" or "RLS enabled but
  no policies defined".
- No negative tests (anon user, authenticated-but-wrong-user) for sensitive
  tables (`profiles`, `orbit.*`, `wallet.*`, payment tables, audit logs).

### Plan

See `rls-audit-checklist.md` for the methodology:

1. Enumerate all tables in sensitive schemas.
2. Assert `rowsecurity = true` for every table.
3. Assert at least one policy per `(cmd, role)` tuple we expect to allow.
4. Write parity tests with `pgtap` or a Deno test harness exercising each
   policy with three personas: anon, owner, other-user.

## 3. HTTP security headers (CSP / HSTS / Permissions-Policy / Referrer-Policy)

### Current state (`easy-locs-ea1eb0ed/public/_headers`)

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(self), microphone=(self), geolocation=(self), payment=(self), interest-cohort=()`
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Embedder-Policy: credentialless`
- Full CSP with `default-src 'self'` and explicit allowlists for Supabase,
  Stripe, Mapbox, Sentry, PostHog, Google Fonts.

### Gaps

- CSP still needs a **report-uri / report-to** endpoint so we learn about
  production violations instead of them failing silently.
- IONOS deployment target must be verified to actually serve `_headers`
  (Netlify/Cloudflare honour this file natively — for IONOS we need to
  confirm via `curl -I` on prod or serve the headers from the app shell).
- Meta-tag `Permissions-Policy` in `index.html` duplicates the HTTP header
  but lacks `interest-cohort=()` — harmless, but worth aligning.

### Plan

1. Add a lightweight Supabase edge function `csp-report` that ingests CSP
   reports and writes to `system.csp_reports` (rate-limited, no auth).
2. Append `report-uri https://<project>.supabase.co/functions/v1/csp-report;`
   and `report-to csp-endpoint;` to the CSP + add the `Report-To` header.
3. Add a prod smoke test (curl-based) that asserts each header is present.

## 4. Secrets — central storage, rotation, leak detection

### Current state

- A dedicated secret scanner `scripts/secret-scan.sh` runs as a CI job
  (`.github/workflows/secret-scan.yml`) on every PR/push. Patterns cover
  Stripe, AWS, GitHub, OpenAI, Anthropic, Supabase `sbp_`, generic PEM keys,
  JWT-looking Mapbox tokens, and URL-embedded DB creds.
- Last manual audit (`docs/security-audit-2026-04-16.md`) found a single
  real leak (`SUPABASE_ACCESS_TOKEN_NEW` in `.replit`), already remediated
  with rotation + Replit Secrets.
- No formal rotation calendar.

### Gaps

- No rotation SOP documented → added in `secrets-rotation.md`.
- `secret-scan.sh` only runs on PRs; it is also invoked from the post-merge
  hook, but not on a scheduled basis against the deployed repo.

### Plan

1. Adopt the rotation schedule in `secrets-rotation.md` (every 90 days for
   service-role keys, on-incident for external vendor keys).
2. Add a weekly scheduled run of `secret-scan.sh` in CI to catch leaks that
   bypass the PR gate (e.g. force-push bypass).

## 5. Orbit E2EE audit

### Implementation

- `src/lib/orbit-crypto.ts` — ECDH P-521 + AES-256-GCM + HKDF-SHA-512 +
  96-bit random IV + 128-bit GCM auth tag, domain-separated info strings,
  protocol version 2.
- `src/lib/orbit-double-ratchet.ts` — Signal-grade double ratchet (ECDH
  P-256 DH ratchet + HKDF-SHA-512 symmetric ratchet + skipped-message-key
  cache, `MAX_SKIP=256`).
- `src/lib/orbit-x3dh.ts` — X3DH preKey bundles (IK/SPK/OPK), 10 one-time
  prekeys generated per device by default.
- `src/lib/orbit-keystore.ts` — IndexedDB store; private keys marked
  non-extractable when the Web Crypto API allows it.
- `src/lib/orbit-session-manager.ts`, `src/lib/e2ee/x3dh-prekey.ts`,
  `src/lib/orbit-file-encryption.ts` round out the stack.

### Audit findings

See `e2ee-orbit-audit.md` for the full checklist. Short version:

- ✅ Correct primitives (ECDH, AES-GCM, HKDF) with strong parameters.
- ✅ Per-message unique IVs derived from CSPRNG + chain-key ratchet.
- ✅ Forward secrecy via DH ratchet; future secrecy via chain-key rotation.
- ⚠ No automated test harness asserting tamper detection, replay rejection,
  or skipped-message-key exhaustion — needs a dedicated Vitest suite.
- ⚠ Recovery story for a lost device is implemented but not documented; a
  user-facing flow + a safety-number re-verification prompt on key change
  should be added to the UX.

## 6. CI — SAST + dependency audit + HoundDog

### Current state

- `.github/workflows/secret-scan.yml` — present, runs on PR/push/dispatch.
- `.github/workflows/bundle-size-gate.yml` — present.
- No SAST (Semgrep) or dependency-audit CI gate. Manual runs via the
  `security_scan` skill are the only signal.

### Actions taken

- Added `.github/workflows/security-audit.yml` which runs on every PR, push
  to main, and on a weekly schedule:
  - `npm audit --omit=dev --audit-level=high` fails the build on any high /
    critical vulnerability in runtime deps.
  - `semgrep ci --config p/owasp-top-ten --config p/javascript --config p/typescript --config p/react --severity=ERROR`
    blocks on any ERROR-severity finding.
  - Runs the local `scripts/secret-scan.sh` as a secondary belt-and-braces.

### Gaps

- HoundDog CLI was flaky in the last manual run; its CI integration is not
  yet added. Track as a follow-up once the CLI is stable.
